# 设计能力

输入是用户本次请求、已确认决定、现有项目证据及交付终点；输出是足以支持下一步的设计或明确的待决问题，不是自动实施授权。

## 读取与分流

先实际读取主 Skill `fucxxx-codex-spec` 及其 `references/design-and-plan.md`，使用其中的范围依据、问题定位、MVP 和文档恢复规则。查找顺序与主入口一致：先用有效 AGENTS.md 登记的 Skill 包根或主入口，再用宿主提供的真实入口，最后才是未安装的仓库并列布局 `../fucxxx-codex-spec/SKILL.md`。安装后不假定相对布局。直接调用本能力时也要找到主入口；不可用则说明依赖缺口，继续可做的只读调查，不编造项目契约或自动安装。主入口只读取一次以获取共同约束，不再次派回本能力循环。

请求已足够明确就使用已有答案。小改动走主入口轻量路径；只读审阅不写设计。正式接入另由 init 处理，使用设计方法不自动修改 AGENTS.md。

## 从真实需要形成方案

1. 读取当前场景、实现与失败证据，按共同参考区分背景、目的、限制及候选原因。需求不清时先问最影响方案的问题，例如“最近一次遇到这个问题时，你在做什么、希望最后得到什么？”不逐项问卷、不重新确认已有答案。能从项目读取的事实先调查。
2. 明确成功结果、非目标及“即使程序能运行也算失败”的情形。核对平台、接口、资源等选择由谁决定：用户已定的保留；普通内部选择自行处理；影响产品目标或成本的待决项提出具体推荐与代价，不把 Agent 默认值写成用户决定。
3. 存在实质取舍时比较少量可行方案，说明各自作用点、证据、代价和未验证假设。依据当前结果选最小真实链路；不是优先堆角色、框架或只掩盖症状。已有方案足够时不要为了比较制造替代方案。
4. 对会影响方向的理解，用具体场景和结果简短复述；不强制固定字数或每轮确认。只有缺失答案会实质改变方案时才等待用户，继续不受影响的授权工作。
5. 关键未知使用现有参考的有界验证方法。原型需要相应授权；说明它证明哪一层、哪些判据未覆盖。原型结果只作为证据，不能自动变成正式交付。

## 总设计与当前 MVP

采用主包的 `assets/master-design.template.md` 与 `assets/mvp-design.template.md`，复用项目既有位置。总设计保留用户结果、组成职责、关键流和不变条件；只细化当前 MVP 的完整可验收链路、必要接口、错误语义和明确非目标，不按目录机械拆分。

候选实现、已定契约和未来项分开写。MVP 提取和新增任务始终核对用户确认来源，不能自行扩写总设计后声称新增范围已批准。设计不提前替执行者决定无关细节，也不能留下会改变用户行为的空白让执行者猜。

## 从实施者角度检查

交付前，以不了解聊天历史的实施者角度阅读设计：如果只能依靠这些文档制定计划，哪些猜测会实质改变结果？核对目标、输入输出、职责、失败行为和验收是否足够；跳过合理内部选择及措辞偏好，不固定问题数量。

复杂设计且有委派授权与工具时，可让独立评估者只读设计及必要项目证据，返回“必须回答的问题、为何影响计划、重要性”，不要向其灌输推荐答案。否则自行检查并说明，不把自检称为独立评审，也不因缺少子会话阻塞普通设计交付。

处理检查结果：已有证据能回答的补入相应段落；普通内部选择自行决定并注明；只有改变目标、契约、验收或成本的实质问题才交给用户。不要让评审建议自动变成本轮需求，反例处理遵守共同范围规则。

## 返回与继续

主会话将产物链接、已定范围、未决项和允许继续到哪里回到原请求。需要恢复时更新同一 handoff。只要求设计就在设计终点交付，不生成 plan 或实施；明确要求先审阅就停。已授权后续工作且条件具备时，由主入口读取计划能力继续，不增加固定阶段批准。不得因选用此能力自动 commit。
