# 计划能力

输入是当前目标、权威设计及基线、授权边界；输出是执行者无需重猜设计即可使用的 plan。计划组织执行，设计仍是契约来源。

## 读取与进入条件

按主入口「能力读取」实际读取主 Skill `fucxxx-codex-spec`（本仓库内为 `../fucxxx-codex-spec/SKILL.md`）、其 `references/design-and-plan.md`，以及项目当前设计和已有活动 plan。主入口不可用时按「缺口处理」继续可做的只读分析。

只读审阅只报告；小改动走主入口轻量路径。实施 plan 只承接已定且获授权的部分。发现关键契约缺口时，指出证据与影响并回到设计处理；重要未知写成验证 plan，产品行为留给设计决定。已明确的需求直接沿用。

## 组织可执行任务

使用主包 `assets/plan.template.md`，按主入口「资料归属」保存到既有项目资料位置。先核对真实代码结构、职责和现有测试入口，再安排任务；只列当前需要的修改位置。

每个任务以可观察产出为单位，准备、配置和文档归入它们服务的交付；只在能独立验证且接口清楚时拆开。任务间存在依赖就注明顺序；不同层的半成品归入同一交付，不各自当成 MVP。

让执行者明确以下内容：

- 输入来源、输出使用者，以及跨任务交接的接口名称、参数、返回值、错误语义；设计已固定的值准确传递，其余普通内部细节留给执行者。
- 涉及文件与直接依赖、为何服务当前目标、改动作用点；范围引用设计。
- 关键测试输入及断言、实际可运行命令和预期结果。必要时给简短测试示例；常规实现只写判据，不预写完整函数体。尚无测试入口时明确需要建立什么，并把拟建命令标为尚未验证。
- 新行为或修复如何用失败证据／必要测试确认，再验证实现和约定集成链路。文案等低风险变更按实际价值决定是否测试，验证要能真正区分对错。

每一步都应能落实为有判据的明确行动；“完善处理”“适当测试”这类没有判据的任务要改写。步骤粒度以可验证为准，不限定执行者每次写哪类代码。计划长于设计不自动是错，但大量重复代码或决定不了任何事的文字应删去。

## 自查与交接

完成后对照设计检查：每项当前验收是否有承担任务；上下游接口和值是否一致；原始失败与设计直接蕴含的关键反例是否覆盖；任务输出、验证与结果位置能否对应。只补实际缺口；相邻优化按主入口「范围依据」延后。

修正本 plan 内的普通错误；实质设计变化交主会话更新权威设计及受影响计划。用户已选定执行方式就保留；未指定时，在授权与工具允许范围内选合适方式。派单写入归属、未提交依赖及契约变更后的恢复按协作参考处理。

### 一个具体例子

总目标是团队任务管理；当前 MVP 是已登录成员创建任务、列表可见且刷新后保留。保留团队权限、持久化和失败反馈，通知与审批仍为后续候选。

假设设计已明确 `POST /api/teams/:teamId/tasks` 的契约，下面是示例而非实际测试记录：

| Plan 位置 | “创建任务 API”任务 |
| --- | --- |
| 工作安排 | 复用登录身份和团队成员校验，接收标题，有权限时保存任务并返回 `201` 和 `id`；结果供页面和列表使用。此任务不实现页面交互。 |
| 验证方式 | 用真实 API 创建，再从列表读回相同 `id`；跨团队请求返回约定 `403` 且不新增记录。使用测试账号与测试数据库，命令取自项目实际入口。 |
| 执行结果写法 | 若创建和读回通过，但跨团队请求仍新增记录：记录各自证据，该任务未通过，先修权限路径。页面提交与刷新未验证，不能标记整个 MVP 完成。 |

若执行者提出先做通知中心，按当前 MVP 目标延后。若权限契约未知，先定位或做有界验证，多租户规则由设计决定，而不是由实施会话自行选择。

## 返回与继续

按主入口「阶段衔接」交回 plan 链接、承接的设计范围和剩余关键问题，按「交付终点」决定停在哪里：只写计划或先审阅就在此交付并保存必要 handoff；已授权开发完成且条件具备时，回到协作参考继续执行与复核。plan 是临时物：执行结果按原模板保存，结束后按协作参考回写设计与长期证据，再移除 plan。
