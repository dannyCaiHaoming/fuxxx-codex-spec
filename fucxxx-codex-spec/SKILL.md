# fucxxx-codex-spec

以当前交付目标为准：总 design 提取 MVP，plan 安排必要工作，执行证据经复核回补设计。项目文件用于恢复；判断以真实代码、运行状态和验证结果为准。

## 先确定本次任务

用户明确要求采用本 Skill，或有效项目指令已声明采用且本次属于相关开发工作时，按下表分流。触发只决定用这套方法判断和推进；建立哪些资料、做到哪一步，由本次请求按「交付终点」决定。

核对项目根、适用指令、已有资料及相关未提交改动。资料根采用项目已确认的路径，默认 `<项目根>/fucxxx-codex-spec/`。**本 Skill 包与项目资料目录用途不同**：项目进度只写进项目资料根；遇到同名目录，先辨明它是 Skill 包还是项目资料，再决定是否写入。

| 当前请求 | 处理与按需阅读 |
| --- | --- |
| 正式采用、修复项目接入 | 读取 `fucxxx-codex-spec-init`；有接入授权才合并 AGENTS.md、按需建立资料。 |
| 需求澄清、总设计、MVP 或设计审阅 | 读取 `fucxxx-codex-spec-design`；只处理当前交付。 |
| 编写／审阅实施或验证 plan | 读取 `fucxxx-codex-spec-plan`；关键设计未定时先补设计。 |
| 实施、委派、恢复 | 读 [执行与恢复](references/execution.md)（执行参考）的对应部分，再读取指定设计和存在的活动 plan。 |
| 复核、回写、收口、提交 | 读 [复核与收口](references/closeout.md)（收口参考）的对应部分。 |
| 小修复、文案或简单配置 | 核对相关约束后直接修改、验证；MVP、plan 和子会话只在确有设计决策或交接需要时建立。 |
| 只读分析、审阅 | 选读相关参考与项目证据，报告结论；资料过期也只报告差异，不写入文件。 |
| 普通问答 | 直接回答。 |

“这次按方法做”属于临时使用：走对应阶段，AGENTS.md 保持原样。已接入项目的日常工作直接分流，无需读取接入能力。已有资料直接复用：已有设计直接进入计划，已有活动 plan 直接恢复执行，小改动不加载设计与计划能力。已读取且仍适用的内容无需重复加载。

## 共同底线

以下条目只在此处维护。init、design、plan 三个能力和两份参考按条目名引用，不另写一份。

**能力读取**　本 Skill 按需读取 init、design、plan 三个阶段能力，它们也要读取本入口。查找任一入口按此顺序：

1. 有效 AGENTS.md 登记的 Skill 包根或具体入口；
2. 宿主提供的可读取入口或已发现的能力名称；
3. 并列布局：主入口读 `../fucxxx-codex-spec-<能力>/SKILL.md`，阶段能力读 `../fucxxx-codex-spec/SKILL.md`。四个目录同在一处时成立，例如本仓库内，或一同装进宿主的同一 skills 目录；分开安装时不成立。

实际读取成功才算已加载；名称、登记行和分流表只是查找线索。本次核实的包根与能力入口记入 handoff；登记缺失或过期时，在接入授权下由 init 补登记。阶段能力读取本入口是为了取得这些共同底线，读完即按自身步骤执行。

**缺口处理**　能力、入口、资料、权限、环境不可用，或关键契约不明时：说明具体缺口，继续不依赖它的授权工作，只暂停受影响部分；需要用户补充时提出具体选择。缺失的能力不要凭记忆复刻其流程，也不要声称已加载或已执行。

**交付终点**　由本次请求决定。只审阅就只读并报告。只写设计或计划就在文档边界交付；留有待审阅、待验证或待实施工作时，按 [设计与计划](references/design-and-plan.md) 的规则更新 handoff。要求开发完成且授权充分时，连续完成必要的设计、计划、实施、验收和收口：写完文档或子会话返回都继续推进，直到用户指定的审阅点或本次交付完成。只为当前 MVP 写计划。暂停与恢复条件见执行参考“分派与执行”。

**范围依据**　用户已确认的目标、验收和后续明确决定是范围的唯一依据。每项新增工作都要直接服务当前验收、必要依赖或已确认约束；未来增强记为候选或延后。缩小范围时保留已确认职责、原失败样例和验收。Agent 自行改写的 design／plan、评审建议，以及“继续执行”这类授权，都不单独构成扩张授权。逐项判断见设计参考“提取当前 MVP”；连续发现关联问题时的累计范围复核见收口参考“复核与返工”。

**阶段衔接**　阶段能力完成后交回：产物链接、已定范围、未决项、停点，以及原授权允许继续到哪里。主会话据此按原请求继续，或在交付终点停止；已完成的阶段不重复执行。切换能力既不是审批点，也不扩大原授权。

**资料归属**　项目只有一套动态状态：总 design、子 design、活动 plan、handoff 与证据；模板由本包 `assets/` 维护。各阶段能力把产物写进项目既有资料位置，复用同一 handoff，不另建目录或台账。主区权威设计和 handoff 由主会话回写。

**提交与外部操作**　commit、push、发布、安装、在业务项目启用、调用外部服务，各自需要用户授权，彼此独立。已有决定照做；用户明确暂不提交就保留本地，不再催问；尚无决定的开发工作在收口后一次问清。只写设计或计划的任务不要求提交业务项目。选用任何能力都不触发 commit，执行 plan 也不逐任务提交。提交内容的核对见收口参考“提交范围”。

**结果如实**　通过、部分通过、失败与未知分别报告，并注明证据层次。读取、派单和自报完成都只是线索，验收以实际证据为准；子区通过不代替主区集成结果。主会话自己检查时注明是自检。无委派能力时由主会话执行或说明限制；子会话、归档和清理状态按实际情况报告。

## 从正确位置继续

- 恢复在途工作：读现存 `handoff.md`，取其中登记的入口，按索引选读总 `design.md`、当前子设计和活动 plan；已有明确派单时直接读指定资料并核对基线。登记入口失效时按「能力读取」重新查找，并说明差异。
- handoff 缺失时先查已有资料再判断状态，没有 handoff 不代表首次采用。状态与实际冲突时指出差异；本次含维护或开发授权才修正。
- 阶段、范围、代码基线变化或上下文压缩后，回读当前目标、约束和进度，核对实际差量与会话状态，按需选读；在途工作先查实际状态，再决定是否派单。
- 用户最新要求改变目标或契约时，先明确它对设计和计划的影响。普通范围内的实现选择自行处理；重大取舍交主会话或用户，契约变化先写进设计再改代码。

| 已有证据位置或 `evidence/` | 支撑结论的必要记录；复用既有测试／CI／报告，只保存定位问题所需的部分。 |

## 方法要点

问题先用用户结果定义，再依据事实选择能改变原因或关键缺口的作用点，候选实现留作候选。设计与计划写清作用机制；复核区分止损、原因修复与后果恢复，症状消失本身不证明原因已消除。证据足以选择可控、可验证的方案，或到达投入边界时，就停止调查。具体方法见设计参考。

主会话负责设计、关键取舍、复核、整合及权威回写；子会话在指定位置交付结果。委派遵循用户和宿主授权；独立上下文不等于独立工作区，写入归属按执行参考明确。存在 design／plan 或委派工作时，按收口参考完成复核、回写、索引同步、结果保存、已结束 plan 移除及安全清理；轻量任务只更新实际受影响的记录。

本包依据设计草案 v0.4 提炼，核心方法自包含，运行不依赖外部 Superpowers。
