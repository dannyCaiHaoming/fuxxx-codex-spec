# 项目接入、协作与收口

按需读取：首次采用看“项目接入”；换会话看“恢复”；委派或实施看“分派与执行”；核对成果看“复核”；完成工作看“回写与收口”和“提交范围”。设计／计划方法见 [设计与计划](design-and-plan.md)。授权、交付终点、范围依据、提交决定等共同底线见主入口，本文不重复。

## 项目接入

正式项目接入的方法与 AGENTS.md 片段统一维护在 `fucxxx-codex-spec-init`，不在此复制。需要正式采用或修复入口时，按主 Skill 的接入分流读取该能力；临时使用和正常恢复不重新接入。AGENTS.md 仍指向主 Skill 并登记包根与阶段能力入口，动态状态继续保存于项目现有资料；恢复时这些登记是查找能力的第一来源，入口实际迁移才按维护接入授权更新。

## 恢复与只读边界

先核对用户本次范围。恢复在途工作读现存 handoff，再选读关联设计和活动 plan，检查实际代码基线、未提交差异、产物和子会话／工作区。文件状态只是线索；没有 plan 不代表未做过。

资料过期时先指出差异。维护／开发授权下由主会话修正；只读分析仅报告，不能因为“先校正状态”而写文件。handoff 缺失时检查已有资料，不自动认定首次采用；在授权内用可验证事实恢复，无法确定的状态标为未知。只要关键契约仍明确，可继续不受影响工作，不重复初始化或派单。

恢复时把现存结果分为已验证可复用、已修改待重验、未执行／受阻，核对其对应的代码和环境。任务勾选、文件存在或旧会话完成声明不是继续下一项的充分依据；在途状态不明时先查实际进程或宿主状态，不能直接重复派发。

阶段切换、基线变化或上下文压缩后，回读目标、约束和当前停点；不用加载全部历史。轻量任务只核对相关材料；需要新增设计或计划时再读设计参考。

## 分派与执行

主会话拥有设计、关键取舍、复核、整合和权威回写。子会话是独立执行上下文，不固定模型；用户可见新聊天需要对应授权，内部 Agent 遵循宿主委派规则。已有同范围授权直接沿用；无委派能力时，按主入口「结果如实」由主会话执行或说明限制。

需要委派时，按实际独立性分工；设计／代码有依赖就按依赖推进，不为并行猜接口。交接采用 plan §0，不另写同内容 brief。轻量任务没有 plan 时，直接给出目标、边界和验证要求。

交接材料必须包含：

- 实际项目／工作区、适用指令、Skill 主入口，以及执行者需要的包根或阶段能力入口；按子会话可解析的位置给出，不把主区相对布局当成通用路径。
- 相关设计与活动 plan 的路径、版本；当前目标、已定范围和验收。
- 任务代码基线及必要未提交依赖，区别本轮新增差量和已有工作。
- 环境、成本、外部操作授权和停止点；交付与证据位置。

未提交设计和依赖要实际提供，不能假设从 HEAD 创建的工作区已经包含它们。无 commit 时可用相关文件快照／差异及必要 hash，不建立全仓清单。路径按真实工作区解释，不把主区绝对路径当成子区可写位置。

独立执行上下文不等于独立工作区。派单时在 plan §0 的执行边界／交付位置或轻量任务原交接中明确实际写入归属：

- 独立工作区：子会话在自己的 plan 副本或已有证据位置保存结果和回写建议，返回主会话；子区设计和 handoff 副本不成为主区权威状态。
- 共享工作区：明确每个执行者可写的文件或结果位置；同一 plan 指定一名维护者，其余执行者返回结果或写指定证据位置，由维护者汇总。修改范围冲突时按顺序执行，不让多个执行者同时回写同一文件，不强制新增 worktree 或账本。

主区总设计、子设计和 handoff 均由主会话统一回写，子会话不直接修改。主会话维护需跨会话跟进的活动表、负责人、工作区、任务依据和状态；直接执行时也由主会话维护这些记录。并发主会话先确定当前协调者，不引入锁服务。

执行者实际读指定设计和存在的 plan；无 plan 任务核对明确交接。开工前核对直接任务间的接口产出与消费，执行时将真实输出与计划判据比较：

- 与预期相符：保存必要结果，继续下一项依赖已满足的工作。
- 实现错误：保留失败输入和环境，按下文方法定位，不改判据制造通过。
- 计划错误：接口名、命令或步骤与权威设计冲突时，在既定契约内作最小纠正；按写入归属由计划维护者同步理由及受影响后续任务，不能只口头绕过。设计契约本身需变化时按暂停与恢复规则处理。
- 证据不足／环境受阻：说明未能验证什么，不能当作程序失败或完成；继续不受影响部分。

计划服从用户已确认的设计，设计本身也以主入口「范围依据」为准。只记录影响后续执行的决定，不逐步新增账本。

已有开发完成授权且条件具备时，主会话按主入口「交付终点」连续推进当前交付所需的设计、计划、实施、复核、整合和收口；普通纠错、必要调查和授权内的有界验证照常继续。完成本次交付后停止扩展，下一 MVP 需要新的授权。

需要暂停的情况及处理：

- 到达用户指定的审阅或交付边界：交付当前成果，记录仍需恢复的工作；不能因“连续推进”越过边界。
- 需要实质改变目标、产品／共享契约、验收或成本范围：子会话报告证据、影响与选项，暂停受影响操作。主会话核对已有决定与授权；已有明确决定直接落实，仍需用户选择或补充授权时才询问。
- 关键契约仍不明、必要权限／环境缺失或已到约定投入边界：保存实际进度，说明阻塞、恢复前提和下一项有价值的动作；继续不受影响的授权工作，不猜契约、不自行扩预算或无限重试。

目标或契约变化获确认后，由主会话先更新受影响的权威设计，再同步活动 plan 的依据、任务和验收，保留有效执行结果并标明需要重验的部分；同步 handoff 中受影响的停点和下一步。通知相关执行者读取更新后的依据、核对实际基线后，才恢复对应执行。没有 plan 时更新原交接即可，不补造计划或重写无关文档；决策未落实到执行依据前不能沿旧计划继续。

任务完成或发生重要变化时，及时在指定位置保存结果并返回状态，由 plan 维护者及主会话同步相应执行记录和 handoff；不把持久化全部留到最后。轻量任务可直接返回差量和验证结果，不强制额外文件。

主会话按需读取紧凑状态，完成或出现实质问题时看详情，不高频轮询。缺少自动唤醒能力时不承诺无人值守跟进。跨聊天发送遵循宿主权限；不能主动发送时由主会话读取状态。

子会话返回：实际结论与证明层次；差量／产物位置和基线；验证证据及未知；设计差异与回写建议；仍在运行或需保存／清理的资源。任务完成后等待复核，不自行开始下一 MVP；主会话继续完成同一授权范围内后续工作。

## 复核与返工

主会话核对目标、实际完整差量、证据版本、原始失败覆盖、实现质量与当前风险。复核输入包含用户确认范围、设计／plan、真实任务基线与产物、执行者结论及未覆盖项。委派审查时明确只读范围，要求每项发现给出位置、触发条件、实际影响和支持证据；评审建议及严重等级不自动构成需求或修复授权。没有证据的判断标为待验证，不报告未读代码。差量从记录的任务基线看到实际交付，包含必要未提交修改，不只看最后一笔 commit；子会话自报完成只是线索。

整合子会话成果时按实际差量合入，保留主区最新设计和 handoff，包括派单后新增的未提交决策；不以子区旧文档副本整份覆盖主区文件。子会话的设计建议由主会话对照当前版本选择性回写；发现实现依赖过期契约时，按“分派与执行”的变更与恢复规则处理，再验收整合结果。

影响已定契约、验收或有证据表明会导致当前使用失败的问题，应在相应交付通过前解决。其他观察只有有后续价值时才延后记录，不自动扩展本轮。关键疑点做定向核查，不用“计划没提到”或审查者级别代替判断。

将新发现纳入本轮阻塞前，说明它属于本次改动引入的回归、当前已确认验收的直接障碍，还是既有相邻问题，并给出失败证据及因果关系。前两类修复所需的直接依赖可以纳入；既有相邻问题只有证据表明会破坏当前承诺时才阻塞交付，不能仅因相关、严重级别或“更稳妥”就加入。不确定时先定向核查，不预先扩建机制。新增永久禁用、调用方式限制、重试上限等产品行为须核对既有契约和授权，不能以防御性修复之名自行改变用户可用能力。

连续修复带出新前置、验证场景持续增加，或复审反复出现相邻问题时，重新对照用户确认的交付边界检查累计范围：当前还缺哪项验收、每个新增阻塞为何不可省略、哪些检查已有有效证据。将判断写回现有 plan／设计的对应位置，无须新台账或固定轮次审批。保留必要正确性与硬性验收，延后没有直接依据的扩展；本轮条件已经满足就收口，不以“再全面检查一轮”无限续接。实质变化仍按“分派与执行”处理；是否构成扩张，按主入口「范围依据」判断。

复核时对照原始场景，检查预期作用机制是否得到支持，以及证据只证明了止损、原因修复还是后果恢复。症状暂时消失不单独证明原因已消除；新证据反驳原判断或同类失败反复出现时，先按设计参考重查相关来源、职责和接口，在现有设计／plan 修正判断，再决定必要差量，不沿错误假设继续叠加补丁或检查。已满足约定的止损目标不因此强制升级为永久修复。

返工先读完整错误、失败输入、相关变更和必要环境，复用最小复现或已有失败记录。沿相关边界检查数据从哪里产生、怎样传递、在哪里首次偏离预期；先用现有日志和正常案例对照，仅在无法区分原因时增加必要观测，不给每层机械加日志或输出秘密。

提出可被反驳的具体假设，并用能区分解释的最小检查验证；一次验证尽量隔离变量，避免混入相邻重构后无法判断哪项起效。检查不支持假设时更新判断，不在原假设上继续叠补丁；无法复现就明确证据不足与下一项有价值的检查。已有证据足够时直接修复，不为了流程重复调查。允许的止损仍按设计参考说明边界，不要求所有任务都找出永久根因。

将实际 blocker、证据、待补差量、保留前提和修复后验收交给执行者。未知原因保持未知，不能编造修复处方或删掉必要前提制造通过。有 plan 时更新 §0；无 plan 时沿原交接修正，不另建返工单。反复失败或修复不断改变相邻职责时，复查原因假设、接口与累计范围；不按固定次数自动升级架构或追加审批。

同一职责的局部修正优先评估续用原有子会话；职责变更、上下文误导、原会话不可用或独立复核需要时再选新上下文。续用仍须核对当前基线；必要独立确认不能因节省往返而取消。

按当前需要选择静态、单元、组件集成、真实入口、实际依赖／模型、用户结果或发布后观察，并非每次要求全部层。先用原失败／最小复现调试，再做受影响回归和约定整体验收。不能拼接不同运行冒充要求同次完成的链路；测试条数、HTTP 200、文件存在和自述均不能单独证明目标完成。

宣称通过前核对验证针对的版本、输入、环境、退出状态和实际输出，指出它支持哪项验收；失败、跳过、仅语法通过或旧版本结果不能包装成当前目标完成。代码或依赖变化使证据失效时重验受影响部分；仍适用的历史证据注明版本和条件后复用，不因再次汇报就重跑。修复须覆盖原始失败，有必要的回归测试应能在旧实现暴露缺口；旧版本验证用隔离副本，不回退当前工作区。工具返回成功但内容不满足判据时仍未通过。

独立复跑针对关键行为或可疑证据，不机械重复全部检查。整合改变了代码基线或组合关系时完成必要主区验收；子区通过不能直接宣称主区通过。主会话亲自实现时说明复核方式，并按主入口「结果如实」注明是自检。

## 回写与收口

仅处理本次实际涉及的文档与资源；轻量任务无需为走完步骤补建文件。只要求设计／计划时，按主入口「交付终点」在文档边界结束。

1. 核对成果和授权，完成必要复核、整合与验收；只获原型验证授权时不顺带合并产品代码。
2. 回写子设计的最终方案、理由、接口、条件、版本、证据层次和限制；修正正文，不追加互相矛盾的日记。更新总设计受影响的决策、MVP 状态及依赖；无架构变化只改摘要和链接。
3. 同步已有文档入口的受影响条目，再由主会话更新 handoff 的当前状态、未整合成果、问题、下一步和提交状态。不等 commit 才同步，不复制运行日志到索引。
4. 将影响后续判断的计划纠错、重要取舍与未解决限制写回相应设计／证据，避免仅留在临时 plan 或聊天里。确认结束 plan 的关键问题、判据、结论和未完成事项已有长期去处，移除该 plan 并清理活动链接；仍有本 plan 承担的执行工作就保留它。失败／证据不足的验证 plan 也可结束，但 MVP 不因此完成。
5. 成果已整合核对或有可靠恢复副本，且没有本任务在途进程后，归档子会话并安全清理临时资源／工作区。更新真实清理结果，失败的单列待处理，不影响已成立技术结论。
6. 交付结果、证据层次、未验证内容和实际资源状态；提交按主入口「提交与外部操作」处理。

保留证据至少能定位问题、输入／环境、版本或未提交差异、方法、实际结果和未覆盖范围。复用既有测试、CI、报告；外部证据不可访问时说明限制，不声称可本地复验。不要保存秘密、私有推理或无用全量日志。

从未提交的 plan 不在 Git 历史中。必要时把最小原判据随证据保存，再移除 plan；不要求归档其全文。设计结论引用长期证据，不能依赖将被删除的 plan。不能删除仍是唯一成果来源的文件。

归档聊天、结束内部 Agent／进程和清理工作区是不同操作，不把归档称为永久删除。永久删除仅在明确要求且宿主支持时执行。检查归档副作用：若会自动创建 Git 快照提交，用户禁止 commit 时不能视作例外；用符合授权且可恢复的方式处理，否则保留成果并注明待清理原因。

## 提交范围

何时提交、是否询问见主入口「提交与外部操作」；需要询问时，一次问清只提交、提交并推送还是保留本地。普通实施选择不需要再次批准。本节只管提交内容。

提交前检查实际差量、分支与目标远端，仅纳入授权内容。文件被本轮修改不代表整文件的改动都属于本轮。核对本轮差量在目标提交基线上是否独立成立：若依赖已有未提交成果且不能安全拆分，说明必要依赖、推荐顺序和各笔范围；授权未覆盖依赖时请求补充决定，不夹带旧工作或提交残缺结果。

push 会带上当前分支其他未推送提交时说明实际范围；push 不等于部署。不重置、暂存或清理无关工作以简化收口，不强制提交全部改动。

## Superpowers 来源与边界

执行偏差处理、调试假设验证、证据核对及审查输入，依据固定 Superpowers 7.0.0 的 executing-plans、systematic-debugging、verification-before-completion 和 code-reviewer 方法适配进本文；许可见主包 LICENSE.superpowers，来源原文与哈希只在仓库 vendor 中溯源。协作方法也曾借鉴 subagent-driven-development，未迁入其脚本或调度流程。运行不依赖外部 Superpowers、ledger、固定评审轮数、模型升级或逐任务 commit。

用户明确要求直接使用外部 Skill 时，先核对具体版本、必需脚本／文件、评审和提交要求。兼容则按实际规则执行；不兼容则说明来源、影响和可行选择，继续不受影响的授权工作。需要新增账本或改变协作方式时明确待决差异，不承诺只换路径即可兼容，也不声称执行完整流程却暗中跳过要求。
