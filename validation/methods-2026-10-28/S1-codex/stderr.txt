# fucxxx-codex-spec

以当前交付目标为准：总 design 提取 MVP，plan 安排必要工作，执行证据经复核回补设计。项目文件用于恢复；判断以真实代码、运行状态和验证结果为准。

## 先确定本次任务

用户明确要求采用本 Skill，或有效项目指令已声明采用且本次属于相关开发工作时，按下表分流。触发只决定用这套方法判断和推进；建立哪些资料、做到哪一步，由本次请求按「交付终点」决定。

核对项目根、适用指令、已有资料及相关未提交改动。资料根采用项目已确认的路径，默认 `<项目根>/fucxxx-codex-spec/`。**本 Skill 包与项目资料目录用途不同**：项目进度只写进项目资料根；遇到同名目录，先辨明它是 Skill 包还是项目资料，再决定是否写入。

## 共同底线

以下条目只在此处维护。init、design、plan 三个能力和两份参考按条目名引用，不另写一份。

**能力读取**　本 Skill 按需读取 init、design、plan 三个阶段能力，它们也要读取本入口。查找任一入口按此顺序：

1. 有效 AGENTS.md 登记的 Skill 包根或具体入口；
2. 宿主提供的可读取入口或已发现的能力名称；
3. 并列布局：主入口读 `../fucxxx-codex-spec-<能力>/SKILL.md`，阶段能力读 `../fucxxx-codex-spec/SKILL.md`。四个目录同在一处时成立，例如本仓库内，或一同装进宿主的同一 skills 目录；分开安装时不成立。

实际读取成功才算已加载；名称、登记行和分流表只是查找线索。本次核实的包根与能力入口记入 handoff；登记缺失或过期时，在接入授权下由 init 补登记。阶段能力读取本入口是为了取得这些共同底线，读完即按自身步骤执行。

**缺口处理**　能力、入口、资料、权限、环境不可用，或关键契约不明时：说明具体缺口，继续不依赖它的授权工作，只暂停受影响部分；需要用户补充时提出具体选择。缺失的能力不要凭记忆复刻其流程，也不要声称已加载或已执行。

**交付终点**　由本次请求决定。只审阅就只读并报告。只写设计或计划就在文档边界交付；留有待审阅、待验证或待实施工作时，按 [设计与计划](references/design-and-plan.md) 的规则更新 handoff。要求开发完成且授权充分时，连续完成必要的设计、计划、实施、验收和收口：写完文档或子会话返回都继续推进，直到用户指定的审阅点或本次交付完成。只为当前 MVP 写计划。暂停与恢复条件见执行参考“分派与执行”。

**范围依据**　用户已确认的目标、验收和后续明确决定是范围的唯一依据。每项新增工作都要直接服务当前验收、必要依赖或已确认约束；未来增强记为候选或延后。缩小范围时保留已确认职责、原失败样例和验收。Agent 自行改写的 design／plan、评审建议，以及“继续执行”这类授权，都不单独构成扩张授权。逐项判断见设计参考“提取当前 MVP”；连续发现关联问题时的累计范围复核见收口参考“复核与返工”。

**阶段衔接**　阶段能力完成后交回：产物链接、已定范围、未决项、停点，以及原授权允许继续到哪里。主会话据此按原请求继续，或在交付终点停止；已完成的阶段不重复执行。切换能力既不是审批点，也不扩大原授权。

**资料归属**　项目只有一套动态状态：总 design、子 design、活动 plan、handoff 与证据；模板由本包 `assets/` 维护。各阶段能力把产物写进项目既有资料位置，复用同一 handoff，不另建目录或台账。主区权威设计和 handoff 由主会话回写。

**提交与外部操作**　commit、push、发布、安装、在业务项目启用、调用外部服务，各自需要用户授权，彼此独立。已有决定照做；用户明确暂不提交就保留本地，不再催问；尚无决定的开发工作在收口后一次问清。只写设计或计划的任务不要求提交业务项目。选用任何能力都不触发 commit，执行 plan 也不逐任务提交。提交内容的核对见收口参考“提交范围”。

**结果如实**　通过、部分通过、失败与未知分别报告，并注明证据层次。读取、派单和自报完成都只是线索，验收以实际证据为准；子区通过不代替主区集成结果。主会话自己检查时注明是自检。无委派能力时由主会话执行或说明限制；子会话、归档和清理状态按实际情况报告。

## 从正确位置继续

- 恢复在途工作：读现存 `handoff.md`，取其中登记的入口，按索引选读总 `design.md`、当前子设计和活动 plan；已有明确派单时直接读指定资料并核对基线。登记入口失效时按「能力读取」重新查找，并说明差异。
- handoff 缺失时先查已有资料再判断状态，没有 handoff 不代表首次采用。状态与实际冲突时指出差异；本次含维护或开发授权才修正。
- 阶段、范围、代码基线变化或上下文压缩后，回读当前目标、约束和进度，核对实际差量与会话状态，按需选读；在途工作先查实际状态，再决定是否派单。
- 用户最新要求改变目标或契约时，先明确它对设计和计划的影响。普通范围内的实现选择自行处理；重大取舍交主会话或用户，契约变化先写进设计再改代码。

## 方法要点

问题先用用户结果定义，再依据事实选择能改变原因或关键缺口的作用点，候选实现留作候选。设计与计划写清作用机制；复核区分止损、原因修复与后果恢复，症状消失本身不证明原因已消除。证据足以选择可控、可验证的方案，或到达投入边界时，就停止调查。具体方法见设计参考。

主会话负责设计、关键取舍、复核、整合及权威回写；子会话在指定位置交付结果。委派遵循用户和宿主授权；独立上下文不等于独立工作区，写入归属按执行参考明确。存在 design／plan 或委派工作时，按收口参考完成复核、回写、索引同步、结果保存、已结束 plan 移除及安全清理；轻量任务只更新实际受影响的记录。

## The Rule

**Invoke relevant or requested skills BEFORE any response or action** — including clarifying questions, exploring the codebase, or checking files. If it turns out wrong for the situation, you don't have to use it.

**Before entering plan mode:** if you haven't already brainstormed, invoke the brainstorming skill first.

Then announce "Using [skill] to [purpose]" and follow the skill exactly. If it has a checklist, create a todo per item.

## Skill Priority

When multiple skills apply, process skills come first — they set the approach, then implementation skills (frontend-design, etc.) carry it out. Brainstorming and systematic-debugging are Superpowers' most common process skills, but the rule holds for any of them.

- "Let's build X" → superpowers:brainstorming first, then implementation skills.
- "Fix this bug" → superpowers:systematic-debugging first, then domain skills.

## Red Flags

These thoughts mean STOP—you're rationalizing:

| Thought | Reality |
|---------|---------|
| "This is just a simple question" | Questions are tasks. Check for skills. |
| "I need more context first" | Skill check comes BEFORE clarifying questions. |
| "Let me explore the codebase first" | Skills tell you HOW to explore. Check first. |
| "I can check git/files quickly" | Files lack conversation context. Check for skills. |
| "Let me gather information first" | Skills tell you HOW to gather information. |
| "This doesn't need a formal skill" | If a skill exists, use it. |
| "I remember this skill" | Skills evolve. Read current version. |
| "This doesn't count as a task" | Action = task. Check for skills. |
| "The skill is overkill" | Simple things become complex. Use it. |
| "I'll just do this one thing first" | Check BEFORE doing anything. |
| "This feels productive" | Undisciplined action wastes time. Skills prevent this. |
| "I know what that means" | Knowing the concept ≠ using the skill. Invoke it. |

输入是用户本次请求、已确认决定、现有项目证据及交付终点；输出是足以支持下一步的设计或明确的待决问题。实施授权仍由原请求决定。

## 读取与分流

先按主入口「能力读取」实际读取主 Skill `fucxxx-codex-spec`（本仓库内为 `../fucxxx-codex-spec/SKILL.md`）及其 `references/design-and-plan.md`，使用其中的共同底线、问题定位、MVP 和文档恢复规则。直接调用本能力时同样如此。主入口不可用时按「缺口处理」继续可做的只读调查；此时没有共同底线可依，项目契约一律留作待定。

请求已足够明确就直接使用已有答案。小改动走主入口轻量路径，只读审阅只报告，正式接入交给 init；本能力不修改 AGENTS.md。

## 从真实需要形成方案

1. 读取当前场景、实现与失败证据，按设计参考区分背景、目的、限制及候选原因。能从项目读到的事实先调查。需求仍不清时，一次只问最影响方案的问题，例如“最近一次遇到这个问题时，你在做什么、希望最后得到什么？”；已有答案直接沿用。
2. 明确成功结果、非目标及“即使程序能运行也算失败”的情形。核对平台、接口、资源等选择由谁决定：用户已定的保留；普通内部选择自行处理；影响产品目标或成本的待决项，给出具体推荐与代价。Agent 的默认值标为建议，与用户决定分开记录。
3. 存在实质取舍时比较少量可行方案，说明各自作用点、证据、代价和未验证假设。依据当前结果选最小真实链路，把作用点放在能改变结果的环节，而不是增加角色、框架或只掩盖症状。已有方案足够时直接采用。
4. 对会影响方向的理解，用具体场景和结果简短复述。只有缺失答案会实质改变方案时才等待用户，同时继续不受影响的授权工作。
5. 关键未知使用设计参考的有界验证方法。原型需要相应授权，并说明它证明哪一层、哪些判据未覆盖。原型结果作为证据使用；要转为正式交付，按设计参考重新接入并验收。

### 一个具体例子

用户反馈“订单列表出现重复订单”，并建议“在列表里把重复的过滤掉”。下面是示例写法，不是实际设计记录：

| 设计位置 | 写法 |
| --- | --- |
| 背景 | 链路是事件投递 → `receive` → store → 列表与原始导出。同一事件 `e1` 被投递两次，store 里就有两条：是重复写入，不只是重复展示。 |
| 目的 | 同一事件只对应一条订单，列表和原始导出都正确；金额相同的不同订单要保留。“列表过滤”只是候选实现。 |
| 限制 | 已确认：投递可能重复，`event_id` 是事件的稳定标识，未知历史数据不清理。可调整：`receive` 目前无条件追加，这只是现有实现。 |
| 作用点与验证 | 在 `receive` 按 `event_id` 跳过已存事件。原始输入后 store 与列表都应为 2 条，整批重放后仍为 2 条；只在列表过滤会让 store 和导出保持 3 条，因此被这条判据否定。 |

如果 `receive` 是不可改的供应商代码，且用户目标只要求列表正确，那么只在列表去重是合理的止损：设计里写明 store 和导出仍有重复、依赖它们的对账可能重复计数，以及重新处理的前提。止损不能写成原因已消除。

## 总设计与当前 MVP

采用主包的 `assets/master-design.template.md` 与 `assets/mvp-design.template.md`，复用项目既有位置。总设计保留用户结果、组成职责、关键流和不变条件；只细化当前 MVP 的完整可验收链路、必要接口、错误语义和明确非目标，并按可验收能力而非目录结构拆分。

候选实现、已定契约和未来项分开写。提取 MVP 和加入新任务时，按主入口「范围依据」核对用户确认来源。会改变用户可见行为的决定写定在设计里，与之无关的内部细节留给执行者。

## 从实施者角度检查

交付前，以不了解聊天历史的实施者角度阅读设计：如果只能依靠这些文档制定计划，哪些猜测会实质改变结果？核对目标、输入输出、职责、失败行为和验收是否足够；合理的内部选择和措辞偏好可以跳过。

复杂设计且有委派授权与工具时，可让独立评估者只读设计及必要项目证据，返回“必须回答的问题、为何影响计划、重要性”；只给它设计和证据，不附推荐答案。否则自行检查，并按主入口「结果如实」注明是自检；普通设计交付照常进行。

处理检查结果：已有证据能回答的，补入相应段落；普通内部选择自行决定并注明；只有改变目标、契约、验收或成本的实质问题才交给用户。评审建议和反例是否纳入本轮，按主入口「范围依据」判断。

## 返回与继续

按主入口「阶段衔接」交回，并按「交付终点」决定停在哪里：只要求设计就停在设计；明确要求先审阅就停在审阅点；已授权后续工作且条件具备时，由主入口读取计划能力继续。需要恢复时更新同一 handoff。

# 计划能力

输入是当前目标、权威设计及基线、授权边界；输出是执行者无需重猜设计即可使用的 plan。计划组织执行，设计仍是契约来源。

## 读取与进入条件

按主入口「能力读取」实际读取主 Skill `fucxxx-codex-spec`（本仓库内为 `../fucxxx-codex-spec/SKILL.md`）、其 `references/design-and-plan.md`，以及项目当前设计和已有活动 plan。主入口不可用时按「缺口处理」继续可做的只读分析。

只读审阅只报告；小改动走主入口轻量路径。实施 plan 只承接已定且获授权的部分。发现关键契约缺口时，指出证据与影响并回到设计处理；重要未知写成验证 plan，产品行为留给设计决定。已明确的需求直接沿用。

## 组织可执行任务

使用主包 `assets/plan.template.md`，按主入口「资料归属」保存到既有项目资料位置。先核对真实代码结构、职责和现有测试入口，再安排任务；只列当前需要的修改位置。

每个任务以可观察产出为单位，准备、配置和文档归入它们服务的交付；只在能独立验证且接口清楚时拆开。任务间存在依赖就注明顺序；不同层的半成品归入同一交付，不各自当成 MVP。

让执行者明确以下内容：

- 输入来源、输出使用者，以及跨任务交接的接口名称、参数、返回值、错误语义；设计已固定的值准确传递，其余普通内部细节留给执行者。
- 涉及文件与直接依赖、为何服务当前目标、改动作用点；范围引用设计。
- 关键测试输入及断言、实际可运行命令和预期结果。必要时给简短测试示例；常规实现只写判据，不预写完整函数体。尚无测试入口时明确需要建立什么，并把拟建命令标为尚未验证。
- 新行为或修复如何用失败证据／必要测试确认，再验证实现和约定集成链路。文案等低风险变更按实际价值决定是否测试，验证要能真正区分对错。

每一步都应能落实为有判据的明确行动；“完善处理”“适当测试”这类没有判据的任务要改写。步骤粒度以可验证为准，不限定执行者每次写哪类代码。计划长于设计不自动是错，但大量重复代码或决定不了任何事的文字应删去。

## 自查与交接

完成后对照设计检查：每项当前验收是否有承担任务；上下游接口和值是否一致；原始失败与设计直接蕴含的关键反例是否覆盖；任务输出、验证与结果位置能否对应。只补实际缺口；相邻优化按主入口「范围依据」延后。

修正本 plan 内的普通错误；实质设计变化交主会话更新权威设计及受影响计划。用户已选定执行方式就保留；未指定时，在授权与工具允许范围内选合适方式。派单写入归属、未提交依赖及契约变更后的恢复按主包执行参考处理。

### 一个具体例子

总目标是团队任务管理；当前 MVP 是已登录成员创建任务、列表可见且刷新后保留。保留团队权限、持久化和失败反馈，通知与审批仍为后续候选。

假设设计已明确 `POST /api/teams/:teamId/tasks` 的契约，下面是示例而非实际测试记录：

| Plan 位置 | “创建任务 API”任务 |
| --- | --- |
| 工作安排 | 复用登录身份和团队成员校验，接收标题，有权限时保存任务并返回 `201` 和 `id`；结果供页面和列表使用。此任务不实现页面交互。 |
| 验证方式 | 用真实 API 创建，再从列表读回相同 `id`；跨团队请求返回约定 `403` 且不新增记录。使用测试账号与测试数据库，命令取自项目实际入口。 |
| 执行结果写法 | 若创建和读回通过，但跨团队请求仍新增记录：记录各自证据，该任务未通过，先修权限路径。页面提交与刷新未验证，不能标记整个 MVP 完成。 |

若执行者提出先做通知中心，按当前 MVP 目标延后。若权限契约未知，先定位或做有界验证，多租户规则由设计决定，而不是由实施会话自行选择。

## 返回与继续

按主入口「阶段衔接」交回 plan 链接、承接的设计范围和剩余关键问题，按「交付终点」决定停在哪里：只写计划或先审阅就在此交付并保存必要 handoff；已授权开发完成且条件具备时，按主包执行参考继续执行，复核按收口参考。plan 是临时物：执行结果按原模板保存，结束后按收口参考回写设计与长期证据，再移除 plan。

# 设计与计划

用于总设计、MVP、重要未知和计划任务。本文维护设计／计划的共同方法：问题定位、MVP 范围的逐项判断、未知去向及 handoff 建立条件；授权、交付终点、范围依据等共同底线见主入口。阶段操作分别由 `fucxxx-codex-spec-design` 与 `fucxxx-codex-spec-plan` 维护，按主入口「能力读取」查找。需要派单或恢复时读 [执行与恢复](execution.md)，复核或收口时读 [复核与收口](closeout.md)。

## 形成足以推进的设计

先读已确认需求、相关实现和证据，区分事实、推断、候选和已废弃方案。澄清提问与方案比较的具体做法见 design 能力。

在现有设计段落中用“背景—目的—限制”定位问题，不另建分析表或固定提问轮次：背景写可观察现象、相关链路和已有证据，区分事实与候选原因；目的写用户要获得的结果，不提前等同于重试、增加 Agent 或某种框架；限制区分已确认要求／权限边界与尚可调整的实现习惯、历史假设，并注明必要来源。用户明确选定的方案仍须尊重，不能借重新定义问题擅自替换。

据此说明方案改变哪一环、通过什么机制达成目标，以及什么结果会支持或反驳该判断。优先检查直接上游的数据来源、职责和接口，比较少量可行作用点的效果与总代价；不把“更上游”自动视为更正确。原因不明时做能区分候选解释的最小检查，证据足以选择可控且可验证的方案或到达投入边界就停止调查，不追溯无关历史。MVP 的最小范围是达成当前结果所需的工作，不只是最少修改行数；上游修复也必须遵守已确认范围和契约。

按实际作用区分止损、原因修复与后果恢复，同一方案可以包含其中多项。上游不可控或需先恢复服务时，止损可以是合理交付；说明缓解了什么、原因是否已知／消除、剩余影响及重新处理的前提，不强制把永久修复纳入本轮。只有用户目标与验收本就允许该边界时才可据此收口，不能自行降低要求。小任务用几句话说明即可，明确的原因无需重复研究。

总设计表达用户场景、核心结果、主要组成与职责、关键数据流和接口、不可破坏的约束及整体验收。按可验收能力拆 MVP，可以跨前端、后端、数据和配置；不要把目录或架构章节直接当作交付顺序。

使用 [总设计模板](../assets/master-design.template.md)。只细化当前 MVP，未来保留必要方向和依赖。已有其他规格体系时先复用或给出迁移映射，不能仅因调用 Skill 就建立第二份设计权威。

进入计划的条件：当前目标、范围和可观察验收明确；关键未知已解决，或已有有界验证及各结果的去向。未知部分先做验证 plan，并标明尚未定案。已有实施授权且设计明确时，按主入口「交付终点」直接推进。

设计或 plan 完成后按主入口「交付终点」推进。验证结论足以定案时，可在已有授权内转入实现；仍需实质选择、授权或缺失条件时，按执行参考的暂停与恢复规则处理。

本次获准建立项目设计／计划资料，且留下待审阅、待验证或待实施工作时，由主会话创建或更新资料根的 `handoff.md`，链接实际产物，记录停点、未决问题和授权边界。只交付文档也可能需要恢复入口；结果报告不能替代 handoff。只读请求或用户限定仅输出指定文件时不额外写入，交付时说明尚无恢复入口。

## 提取当前 MVP

使用 [子设计模板](../assets/mvp-design.template.md)，顶部写清总目标关联、一个明确结果、最小验收链、必须保留的职责和本轮不做的事。技术试验可独立验收，但不能因此宣称用户已获得可用产品。

每次提取子设计、写计划、加入新工作、发现反例及复核时，判断：**省略这项会使当前验收失败，或违反已确认约束吗？**

判断依据见主入口「范围依据」。保留这些决定的可定位依据，复用设计中的既有说明或来源引用即可。若文档已被自行扩大，指出差异，并在维护授权内纠正受影响部分：新增内容退回为待确认候选，已有成果保留。

- 会：纳入最小必要范围；实质改变目标、共享接口、验收或成本时说明取舍，由主会话／用户决定。
- 不会：延后或不记录；只有有价值的延后项才写重新考虑的触发条件。
- 不确定：做最小检查，不先搭建通用平台或完整治理系统。

缺口会使实际运行违反既定边界时，只暂停受影响运行。

同一子设计可以同时有已定部分、待验证候选和延后项。实现 plan 只承接当前已定且获授权部分；一份 plan 完成不能把整个设计／MVP 标为完成。

分别表达设计、实现、验收、交付状态。例如“方案已定、已整合、静态检查通过但真实入口未验证、本地未提交”。不强制状态机，不把 commit 当成验收。

共享规则由总设计或指定的唯一子设计承载，其余引用。总设计委派的细节以对应子设计为准；改变总设计不变条件须回主会话处理。文档与代码不符时指出差异，不能用文档覆盖事实。

## 重要未知：先验证，再定实现

先在子设计记录问题、为何阻碍当前 MVP、候选方案及代价、最小检查、成立／不成立／证据不足后的去向，再按需写验证 plan。已有资料足以回答时直接调查，不为模板新增研究任务。

验证可以包含获授权的可逆原型。结束于足够支持决策的证据或约定投入边界：

- 成立：回写适用版本、条件和选定契约。
- 不成立：保留反例，采用备选或调整设计。
- 不足：写清缺少什么、影响和下一项有价值的检查，不无限研究相邻问题。

原型代码只在选择性复用时进入产品：先核对当前设计与主区基线，接入后完成验收。验证 plan 可结束并删除，MVP 仍可能未完成；删除前按收口参考保存有用判据与结论。

## 写可交接的 plan

具体任务组织、接口自查和交接方法由 `fucxxx-codex-spec-plan` 维护，按主入口能力路由实际读取。使用本包 Plan 模板，计划只承接当前设计；作用点、范围依据、未知去向服从本文，执行服从执行参考，收口服从收口参考。不在此重复另一套任务步骤。

## 小改动与设计变化

文案、简单配置或既定行为修复：核对约束后直接修改和验证；有相关子设计时复用，没有时直接修改。plan、子会话和完整收口只在设计决策、交接或恢复确有需要时增加。

只更新实际受影响的说明、验收结论或限制。一次完成且无待交接状态可直接报告；有在途工作、阻塞或待恢复下一步时由主会话更新 handoff。小改动若变成目标／契约变化，再按重要取舍处理；验收要求不因任务小而降低。

# Brainstorming

You are very good at building. You build what you believe your human
partner wants, and that belief is usually thinner than it feels. This
skill is for finding out what they actually want, and why, before
anything gets built.

People often haven't finished working out what they want. Good questions
help them think it through. When you understand the why, you make the
hundred decisions they never mention the way they would have made them.

## First: What Do You Actually Know?

Before you reply, ask yourself: what do I know about what they want, and
why?

- **Everything that matters is in the request** ("make the icon cornflower
  blue"). This is a quick, clear task. Do it, and say what you did.
- **Something non-trivial is missing.** Start the conversation.

## Your First Message

Your first message is two things, in this order:

1. One line letting them know that if they'd rather skip the questions and
   have you just start, they can say so. If they take you up on it, this
   skill is done: state any significant how-it-gets-made choice
   (platform, language, medium) in one plain line, then do what they
   asked through the normal workflow.
2. One open question that gets them describing. Ask about a real moment
   or a concrete picture: "What's the moment you find yourself wishing
   this existed?" or "Tell me about the people who'll be in the room."

That's the whole message.

## The Conversation

Each message ends with one question: a single sentence with no list of
example answers hanging off it. Use plain language, pitched just a little
above where your human partner is. Match their vocabulary; never use
process jargon.

Be clear and concise. Lead with what matters. Avoid jargon. When you
report what you found, give them the most important findings and offer
the rest.

**Get them describing.** Open questions come first. Their own words carry
intent that your options can't. Offer a short menu only when they're
stuck. When they say "just guess" or "what do you think?", propose
something concrete.

**How it gets made.** Every project rests on choices about medium, tools,
materials, and resources: the platform, programming language, and
libraries for an app; the medium for a piece of art. Find out early which
of those choices they want to make, which they're handing to you, and what
they already have to work with. Someone with strong views or skills will
want to talk it through. Someone counting on you needs sensible defaults,
said in plain words. When there's existing work, build on what it already
uses. Any choice you make goes in the design as your call, never as
something they agreed to.

**Ground to cover.** This is territory, not a script. Never read these
out as questions:

- what kind of thing this is, and what makes it special
- why now, and what success looks like to them
- goals, non-goals, and anti-goals (what would make this a failure even
  if it technically works)
- prior art: what they've seen elsewhere, loved or hated
- current state: what exists now, what they've tried
- the details they care about

**Questions that work** anchor in specifics: "Walk me through the last
time...", "If it could only do one of these well, which?", "What would
make you wince if I got it wrong?" A guess they can correct ("I'm
guessing this is because X keeps biting you?") often beats a question.

**Offer recon.** Once you have a bit of grounding and looking would help,
offer to go look: their codebase or project, their own files and data,
or the web. Say what you'd look for. They decide whether you go.

**Think wide privately.** Before you propose anything, come up with
several ideas and drop the weak ones, including any that fight what
they've told you about why. Show the comparison only when it helps them
decide.

**Show, don't tell.** Offer the visual companion (below) whenever seeing
would help more than reading:

- something they'll look at: a screen, a page, a printout, a sign
- a layout or arrangement: of a screen, a room, a schedule
- a flow or a sequence of steps
- options that would look different from each other
- a structure that's easier to see than read: a diagram, a timeline, a map

Once they've accepted, use it for mockups to react to, side-by-side
options, and throwaway prototypes they can click.

**Spike to feel things out.** Agentic work is waterfall, but very, very
fast. A quick throwaway build is often the cheapest way to learn what
they want or whether something works. Offer one when it would help.
When they just want to spike, get out of the way. Spikes get no tests
or minimal ones, aren't bulletproof, and skip the plan, implementation,
and review process. Bring what the spike taught you back into the
conversation.

## Play It Back

Play back as you go. As soon as you understand one part well enough to
describe it (what it's for and who it serves, say, or how one piece
behaves), describe that part back in about 200-300 words, then return to
questions about the next part. Playback and questions alternate through
the whole conversation; the last chunk covers whatever is left.

Mark anything you're guessing as your guess; only what they said goes in
as theirs. End each chunk by asking what's wrong or missing.

Before you send a chunk, check it: does it describe something they'll
look at, like a page, a screen, a schedule, or a printout? If so, and
they haven't seen the visual companion offer yet, send the offer instead
(its own message, below) and hold the chunk for the next message. Once
they've accepted, put a mockup next to the description.

## Size the Work

Once you understand what they want, pick a size and say it in plain
words. They can override it.

| Size | The full description | Then |
|------|----------------------|------|
| A quick, clear task | the request itself | do it |
| A small change | in chat | build it through the normal workflow |
| A project with a written design | a written design document | a full plan (for software: superpowers:writing-plans) |

If it grows mid-task, stop, say so, and step up a size.

If this is really several independent projects, say so, agree on an
order, and brainstorm them one at a time.

## The Written Design

For a project, write a plain document a talented builder in the domain
could plan from without going back to your human partner. Cover:

- intent and the why
- goals, non-goals, anti-goals
- constraints
- the parts of the how they decided, as they decided them
- what's left to the builder

**Where it goes:** in a software repo,
`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed.
Otherwise, ask. Your human partner's preferences override both.

**Builder check:** dispatch a fresh subagent with
`builder-check-prompt.md` in this directory. When you tell your human
partner you're writing it up, say a reviewer will read it first and you
may come back once with a few questions. Don't hand over the document
until the check is back. Sort what the builder asks into three piles:

- **Answered already** by the conversation or the project: put the answer
  in the document.
- **Minor:** a sensible builder could settle it without changing what gets
  built. Settle it yourself and mark it in the document as your call.
- **Theirs:** only your human partner can answer it, and the answer changes
  what gets built.

Bring the "theirs" pile in one message, most important first. Update the
document with their answers, then hand it over with a short list of the
calls you made so they can check those while reading. That's the only
round of questions the check produces. Without a subagent tool, read the
document as that builder yourself.

<HARD-GATE>
Nothing gets built until your human partner approves the full
description: in chat for a small change, the document for a project.
Building includes writing product code, scaffolding, installing
dependencies, creating projects, and invoking an implementation skill.
Reading and exploring are fine.

Two exceptions. If they opted out of the questions, the skill is done
and the gate goes with it. A spike they said yes to may be built; it
stays labeled throwaway, and keeping what it produced is a new request
that comes back through this gate.

After a project's document is approved, the next step is the plan. For
software, invoke superpowers:writing-plans and no other skill.
</HARD-GATE>

## Red Flags

| Thought | Reality |
|---------|---------|
| "I'll offer options to save them effort" | Options steer. Ask them to describe it first. |
| "I'll fill in sensible defaults" | Good. Say them out loud. A default they never heard is one they couldn't reject. |
| "I should explain the process first" | Ask your question. The process shows itself. |
| "They said 'sounds good' to the idea" | Approval covers what you showed them. A description you haven't written isn't approved. |
| "The spike works, I'll keep building on it" | Keeping it is a new request. Back through the gate. |

## Visual Companion

A browser tab for showing mockups, diagrams, and prototypes. It's a
tool, not a mode: accepting it doesn't send every question to the
browser.

**Offer it just-in-time.** Offer it the first time one of the moments
above comes up, never upfront. The offer is its own message with nothing
else in it:

> "This might be easier if I show you. Want me to open a browser tab with some mockups?"

If they decline, stay in text and don't offer again unless they raise it.

**Per question, ask: would they understand this better by seeing it?**
Mockups, layouts, diagrams, and side-by-side designs go in the browser.
Requirements, scope, tradeoffs, and conceptual choices stay in text. A
question about a UI topic isn't automatically a visual question.

If they accept, read `visual-companion.md` in this directory before
starting the server.

# Writing Plans

## Overview

Write implementation plans for an engineer who has not seen this codebase or this spec. Assume they write idiomatic code in the project's language once they know the exact interface and the exact test, and that they will make a reasonable choice wherever the plan leaves one open. What they cannot know is what you decided: which files, which names and signatures, which values from the spec, which tests prove each task. Document those. Give them the whole plan as bite-sized tasks. DRY. YAGNI. TDD. Frequent commits.

**Announce at start:** "I'm using the writing-plans skill to create the implementation plan."

**Context:** If working in an isolated worktree, it should have been created via the `superpowers:using-git-worktrees` skill at execution time.

**Save plans to:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (User preferences for plan location override this default)

## Scope Check

If the spec covers multiple independent subsystems, it should have been broken into sub-project specs during brainstorming. If it wasn't, suggest breaking this into separate plans — one per subsystem. Each plan should produce working, testable software on its own.

## File Structure

Before defining tasks, map out which files will be created or modified and what each one is responsible for. This is where decomposition decisions get locked in.

- Design units with clear boundaries and well-defined interfaces. Each file should have one clear responsibility.
- You reason best about code you can hold in context at once, and your edits are more reliable when files are focused. Prefer smaller, focused files over large ones that do too much.
- Files that change together should live together. Split by responsibility, not by technical layer.
- In existing codebases, follow established patterns. If the codebase uses large files, don't unilaterally restructure - but if a file you're modifying has grown unwieldy, including a split in the plan is reasonable.

This structure informs the task decomposition. Each task should produce self-contained changes that make sense independently.

## Task Right-Sizing

A task is the smallest unit that carries its own test cycle and is worth a
fresh reviewer's gate. When drawing task boundaries: fold setup,
configuration, scaffolding, and documentation steps into the task whose
deliverable needs them; split only where a reviewer could meaningfully
reject one task while approving its neighbor. Each task ends with an
independently testable deliverable.

## Step Granularity

**Each step is one action with a checkable result:**
- "Write the failing test" - step
- "Run it to make sure it fails" - step
- "Implement the minimal code to make the test pass" - step
- "Run the tests and make sure they pass" - step
- "Commit" - step

## Plan Document Header

**Every plan MUST start with this header:**

```markdown
# [Feature Name] Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** [One sentence describing what this builds]

**Architecture:** [2-3 sentences about approach]

**Tech Stack:** [Key technologies/libraries]

**Spec:** [path to the spec/design doc this plan implements — the plan
argues from the spec, so the spec travels with it; executors read both]

## Global Constraints

[The spec's project-wide requirements — version floors, dependency limits,
naming and copy rules, platform requirements — one line each, with exact
values copied verbatim from the spec. Every task's requirements implicitly
include this section.]

## Review Focus

[The five input classes or failure modes the spec implies but no task's
tests exercise that are most likely to bite a person using this software
— one line each, naming the input or condition and the behavior a
reasonable person would expect, most likely first. The spec is a vision
document: it says what the software must do, not everything it will
meet, and its silence on an input is not permission for that input to
break the program. Write the list here, once, with the spec in front of
you. Then, for each line, add the test that pins it to the task that
owns the code, in that task's own step style.]

---
```

## Task Structure

````markdown
### Task N: [Component Name]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [what this task uses from earlier tasks — exact signatures]
- Produces: [what later tasks rely on — exact function names, parameter
  and return types. A task's implementer sees only their own task; this
  block is how they learn the names and types neighboring tasks use.]

- [ ] **Step 1: Write the failing test**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: Run test to verify it fails**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: Implement `function(input: InputType) -> ResultType` in `exact/path/to/file.py`**

One line on the approach when the signature and the test leave a choice
(which library call, which data structure); a code block only for an
algorithm they do not determine.

- [ ] **Step 4: Run test to verify it passes**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## What a Step Contains

A step is done when the implementer can write exactly one reasonable thing
from it. That is the whole requirement: unambiguous, not complete. Each kind
of step carries what makes it unambiguous and nothing more:

- **A test step:** the test's name and its assertions, as code, with the
  spec's exact values in them.
- **A code step:** the exact signature (name, parameters, return type), the
  file it lives in, and the specific values the spec pins. The implementer
  writes the body. A body appears only for an algorithm the signature and
  tests do not determine, or for exact copy the spec fixes.
- **A verification step:** the command to run and the output that means it
  passed.
- **A reference to another task:** that task's Interfaces block says what
  to use; the plan does not repeat that task's code.

A plan is the set of decisions the implementer cannot make alone. A plan
longer than the code it describes has written the code instead. Lines that
decide nothing ("TBD", "handle edge cases", "add appropriate validation",
"write tests for the above", a type or function no task defines) are the
opposite failure, and the self-review catches both.

## Self-Review

After writing the complete plan, look at the spec with fresh eyes and check the plan against it. This is a checklist you run yourself — not a subagent dispatch.

**1. Spec coverage:** Skim each section/requirement in the spec. Can you point to a task that implements it? List any gaps.

**2. Step scan:** Every step must let the implementer write exactly one reasonable thing, and no step may carry more than that: a line that decides nothing is a gap, a function body the signature and tests already determine is a transcript. Fix both.

**3. Type consistency:** Do the types, method signatures, and property names you used in later tasks match what you defined in earlier tasks? A function called `clearLayers()` in Task 3 but `clearFullLayers()` in Task 7 is a bug.

**4. Review Focus:** For each input class or failure mode the spec implies, is there a task whose tests exercise it? The five uncovered ones most likely to bite a person go in the Review Focus section, and each line there gets its test added to the owning task. An empty section means you checked and found none, not that you skipped the check.

**5. Proportion:** Compare the plan's length to the spec's. A plan several times longer than the spec it implements is a transcript of the program, not a plan. If code blocks are most of the document, replace bodies with signatures, test names and assertions, and check that each step is still unambiguous.

If you find issues, fix them inline. No need to re-review — just fix and move on. If you find a spec requirement with no task, add the task.

## Execution Handoff

After saving and self-reviewing the plan, link it for your human partner
to read. If they have already explicitly supplied an execution method, ask
them to review the plan and confirm it captures what they want; wait for that
review before implementation, then use the preserved method. Otherwise, ask
them to review the plan and choose an execution method before implementation.

**When no execution method has already been supplied:**

**"Plan complete and saved to `docs/superpowers/plans/<filename>.md`. Please review the plan. Which execution approach would you prefer?**

- **Subagent-driven** - A fresh subagent implements each task and a fresh reviewer checks it before the next one starts, then a whole-branch review at the end. Most thorough; costs a fresh context per task and per review.
- **Native** - I implement every task myself in this session, the way this harness runs work, then one fresh reviewer on the most capable model checks the whole branch. Cheapest and fastest; no independent review until the end. Runs well with a mid-tier session model, since the plan carries the design.

**For this plan I recommend <one of the two>, because <one sentence from the plan: how much the tasks depend on each other's interfaces, how many there are, what a shipped mistake would cost>. Does the plan capture what you want, and which approach should we use?"**

**When an execution method has already been supplied:**

**"Plan complete and saved to `docs/superpowers/plans/<filename>.md`. Please review the plan. Does it capture what you want?"**

**If Subagent-driven chosen:**
- **REQUIRED SUB-SKILL:** Use superpowers:subagent-driven-development

**If Native chosen:**
- **REQUIRED SUB-SKILL:** Use superpowers:executing-plans

## 设计与接口

以下标为“要求”的内容来自 README；其余为本次推荐、待随文档审阅的设计决定。

| 接口 | 输入与输出 | 行为和错误 |
| --- | --- | --- |
| `add_task(path, title)` | path 为字符串或 pathlib.Path，title 为 str；返回含 `id`、`title` 的 dict | 要求：先 strip，空标题抛 ValueError，不写文件。建议：读取后追加，保存成功才返回；存储规范化后的标题 |
| `list_tasks(path)` | 同样的 path；返回任务 dict 列表 | 要求：文件不存在返回 []。建议：只读、不创建文件；按新增顺序返回，每次从磁盘读取 |

推荐存储为 UTF-8 JSON 数组，例如 `[{"id": 1, "title": "中文任务"}]`，使用 `ensure_ascii=False` 保存可直接阅读的中文。允许重复标题，但每个任务 ID 不同；不共享返回对象与进程内存储缓存。

推荐 ID 为正整数：空列表从 1 开始；每次从文件中读取最大 ID 后加 1。唯一性边界是有效数据文件上的串行调用，重启后继续增长；不同文件可复用相同 ID。不承诺并发新增不丢失。

调用者负责提供存在的父目录和有效任务文件，程序不递归创建目录。读文件仅将 FileNotFoundError 视为文件缺失；权限和其他 I/O 错误向上抛出；非法 JSON 保留 JSONDecodeError，不将其当空列表覆盖。有效文件结构为上述程序生成的任务数组；人工修改形成的其他合法 JSON 结构不在当前输入契约内，不增加通用 Schema 验证器。

空标题必须在读取或打开写入文件之前拒绝：无论文件缺失还是已有内容，都不能创建或改动文件。不承诺非 str 标题的统一异常类型。

本轮推荐直接读取、追加、写回 JSON。原子替换、断电保证和并发事务均不属于当前需求；正常保存成功后的跨进程读回属于验收。私有 helper 命名、JSON 缩进等普通细节留给实施者，不拆分存储框架。
