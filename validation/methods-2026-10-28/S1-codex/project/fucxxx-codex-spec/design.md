## 整体设计

复用 `app.py`，公开 `add_task(path, title)`、`list_tasks(path)`，接口详细契约以当前子设计为准。调用者拥有路径选择；函数负责标题处理、读取、ID 分配、追加及保存；文件承担跨调用、跨进程持久化。`test_app.py` 通过真实文件和新 Python 进程验证链路。

数据流：调用者 → 标题校验 → 读取指定文件 → 分配唯一 ID → 追加并保存 → 返回任务；重新启动调用者 → 读取同一文件 → 返回任务列表。不得只靠进程内缓存证明持久化。

建议采用单个 UTF-8 JSON 数组，保持新增顺序；不增加服务、存储接口框架或插件发现机制。文件格式与错误语义是本次提出的待审阅设计选择，不冒充 README 已定内容。

### 插件加载器评估

| 方案 | 对当前目标的作用 | 成本与判断 |
| --- | --- | --- |
| 直接 JSON 文件读写（推荐） | 直接补齐新增与持久化链路 | 一个模块即可实现和验证 |
| 先实现插件加载器 | 当前没有第二、第三种存储，不能增加本轮验收覆盖 | 新增插件发现、注册、生命周期和错误契约，扩大调试面，延后 |

不做加载器不会使任何当前验收失败。README 明确排除插件框架，旧笔记意见属于历史候选，不覆盖当前范围。等真正需要第三种存储时，比较实际存储差异，再决定普通函数分派、存储接口或动态加载是否必要；不预留空插件骨架，不把候选自动升级为承诺。
