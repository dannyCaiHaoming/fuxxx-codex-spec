## 2026-10-28：结构检查脚本化

此前每轮验证都手工重做同一组检查，清单哈希算法只以散文形式记在本文，并且 2026-10-25 那轮把 `git diff --no-index --check` 的"有差异"退出码误判成空白检查失败。现把这组检查固定成 [tools/check-package.py](../tools/check-package.py)：包结构、YAML 元数据、Markdown 围栏、本地链接（含锚点警告）、Git 空白诊断、vendor 来源哈希与包清单 SHA-256，一次跑完并按失败项返回退出码。

脚本不修改仓库，唯一写入是显式 `--write-manifest`；只用标准库，不安装依赖。`tools/` 属于仓库维护工具，不在发行的四个目录内，Skill 运行不依赖它。几处与历史检查有关的取舍：

- 空白检查只按是否有诊断行判定，忽略仅表示"有差异"的退出码；不在 Git 工作树内（提取出的包目录、validation 里的非 Git 样例）退回为行尾空白与 CR 的文本检查，而不是跳过。
- YAML 优先用 Ruby Psych 并强制 `-E UTF-8`（否则中文 frontmatter 报 invalid byte sequence in US-ASCII）；无 ruby 时退回内置最小解析器，并在报告里警告这不等于通过真正的 YAML 解析器。
- 两条样例故意保留的断链（init 的"主入口不可用"分支）登记为预期，单独计数，不混进失败。
- 锚点未匹配标题只警告不失败，因为锚点规则随渲染器变化。

自检：对当前工作版本运行，7 项全部通过，复算出的包清单 SHA-256 为 `ee4f7a93c4018913ca80e73cf60f9e81ad1ba10ee01f4663e3007b85c203d29e`，与上一节手工计算的值一致；`--scope repo` 得到 252 条有效本地链接加 2 条预期断链、203 个 Markdown 文件围栏成对，与此前手工结果相同。另在临时副本中逐项注入 name 不符、未闭合围栏、断链、行尾空白、vendor 文件篡改和错误预期哈希，六类全部被报出且退出码为 1；在无 ruby、无 Git、不含 vendor 的副本中确认退回路径生效、警告如实出现，且清单哈希仍为同一值。首版曾在非 Git 目录把 git 的用法报错当成 258 条诊断（反而漏掉真实的行尾空白），并让解析器退回警告在有失败项时被吞掉，两处已修复后复测。

本节只是把既有检查固定下来，没有改动任何 Skill 规则，包清单哈希与上一节相同。脚本自身没有单元测试，上述为一次性注入验证。未安装、commit 或 push。

## 2026-10-28：资料文件命名软默认

主入口规定了 `designs/`、`plans/`、`evidence/` 放什么，但没有说文件怎么命名。历次样例已经出现三种写法：`designs/title.md`、`designs/mvp-1.md`、`designs/mvp-01-title.md`。多个 MVP 并行或跨会话恢复时，这种差异会让人和模型都难以对应设计与计划。

在主入口“信息放在哪里”表格后补一句默认：子设计用 `designs/<短名>.md`，计划用 `plans/<短名>-<用途>.md`（同一 MVP 同时有验证和实施计划时用用途区分），证据用 `evidence/<短名>-<主题>.md`；MVP 编号只写在标题里，不进文件名，重新排序时链接不会失效。项目已有命名约定时沿用。

这是软默认而不是规则：恢复时真正依赖的是 plan 模板中“依据：<子 design 路径>”这类显式链接，不是文件名。模板未改。

## 2026-10-28：安装脚本与三宿主实测

此前仓库没有安装方式，只说“由宿主的 Skill 管理方式完成”；入口登记（A）也一直缺行为证据。本轮在本机三个宿主上落地并实测。包内容未变，测试对象为 `417c6bcc4eeba56bbf4d8e1e39b7171f07aa83a0659c39ff5612ad2683042d25`（commit `ab8c7c6`）。

**各宿主的发现位置**取自本机证据，而非记忆：Codex 来自内建 skill-installer 与 skill-creator 文档（`${CODEX_HOME:-~/.codex}/skills`）；OpenCode 来自其内建 customize-opencode skill 和 `opencode debug skill` 的实际输出（项目级 `.opencode/skill(s)/`，全局 `~/.config/opencode/skill(s)/`，并自动加载 `~/.claude/skills/` 与 `~/.agents/skills/`）；Claude Code 为 `~/.claude/skills/` 与项目级 `.claude/skills/`。Codex 的项目级目录没有本地文档可证，脚本暂不支持。

**安装脚本** [tools/install.py](../tools/install.py)：只复制四个能力目录，装进同一个 skills 目录，因此并列布局在安装后同样成立。装完按包清单核对副本，并打印 AGENTS.md 登记值。同名目录不属于本包时拒绝覆盖；已装其他版本时需加 `--force`，旧版备份到 skills 目录之外，因为 OpenCode 会递归扫描 `**/SKILL.md`。脚本拒绝同时对 claude 与 opencode 做用户级安装，以免 OpenCode 发现两份同名 skill。另支持 `--project`、`--dest`、`--link`、`--uninstall`、`--dry-run`。在临时 HOME 中测试了 11 种情形：首次安装、同版本重装、外来同名目录、改动后无 `--force` 与有 `--force`（备份含被改内容）、链接模式、链接改复制、dry-run、claude+opencode 冲突、Codex 项目级、OpenCode 项目级、两种卸载；行为与退出码均符合预期。

**实际安装**：`--host codex --host claude`，复制模式，分别装到 `~/.codex/skills/` 与 `~/.claude/skills/`，两处副本的包清单均为 `417c6bcc`。OpenCode 不单独安装，`opencode debug skill`（不调用模型）确认它从 `~/.claude/skills/` 发现了全部四个能力，37 个 skill 中没有同名重复。附带观察：本会话所在的 Claude Code 在安装后立即列出了这四个 skill；这是运行中的会话，不算新会话证据。
