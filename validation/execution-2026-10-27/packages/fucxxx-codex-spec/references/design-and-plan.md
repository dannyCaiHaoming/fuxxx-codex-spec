# 设计与计划

用于总设计、MVP、重要未知和计划任务。本文维护设计／计划共同约束：问题定位、MVP 范围、未知去向及交付边界。阶段操作分别由 `fucxxx-codex-spec-design` 与 `fucxxx-codex-spec-plan` 维护，按主入口查找，不重复执行两套流程。需要派单、恢复或收口时再读 [协作与收口](collaboration-and-closeout.md)。

## 形成足以推进的设计

先读已确认需求、相关实现和证据，区分事实、推断、候选和已废弃方案。只询问会实质改变当前交付的未知，不重新询问已明确偏好。存在取舍时比较少量可行方案，说明推荐、代价与假设；区分用户已定选择和 Agent 建议。

在现有设计段落中用“背景—目的—限制”定位问题，不另建分析表或固定提问轮次：背景写可观察现象、相关链路和已有证据，区分事实与候选原因；目的写用户要获得的结果，不提前等同于重试、增加 Agent 或某种框架；限制区分已确认要求／权限边界与尚可调整的实现习惯、历史假设，并注明必要来源。用户明确选定的方案仍须尊重，不能借重新定义问题擅自替换。

据此说明方案改变哪一环、通过什么机制达成目标，以及什么结果会支持或反驳该判断。优先检查直接上游的数据来源、职责和接口，比较少量可行作用点的效果与总代价；不把“更上游”自动视为更正确。原因不明时做能区分候选解释的最小检查，证据足以选择可控且可验证的方案或到达投入边界就停止调查，不追溯无关历史。MVP 的最小范围是达成当前结果所需的工作，不只是最少修改行数；上游修复也必须遵守已确认范围和契约。

按实际作用区分止损、原因修复与后果恢复，同一方案可以包含其中多项。上游不可控或需先恢复服务时，止损可以是合理交付；说明缓解了什么、原因是否已知／消除、剩余影响及重新处理的前提，不强制把永久修复纳入本轮。只有用户目标与验收本就允许该边界时才可据此收口，不能自行降低要求。小任务用几句话说明即可，明确的原因无需重复研究。

总设计表达用户场景、核心结果、主要组成与职责、关键数据流和接口、不可破坏的约束及整体验收。按可验收能力拆 MVP，可以跨前端、后端、数据和配置；不要把目录或架构章节直接当作交付顺序。

使用 [总设计模板](../assets/master-design.template.md)。只细化当前 MVP，未来保留必要方向和依赖。已有其他规格体系时先复用或给出迁移映射，不能仅因调用 Skill 就建立第二份设计权威。

进入计划的条件：当前目标、范围和可观察验收明确；关键未知已解决，或已有有界验证及各结果的去向。未知部分先做验证 plan，不冒充已定实现。已有实施授权且设计明确时直接推进，不增加固定确认轮次。

设计或 plan 完成后按本次交付终点推进：仅要求设计时不默认再生成 plan；仅要求计划或明确要求先审阅时交付对应文档；已授权开发完成且具备执行条件时，读取协作参考继续实施与复核，不额外要求一次阶段批准。验证结论足以定案时可在已有授权内转实现；若仍需实质选择、授权或缺失条件，按协作参考的暂停与恢复规则处理。

本次获准建立项目设计／计划资料，且留下待审阅、待验证或待实施工作时，由主会话创建或更新资料根的 `handoff.md`，链接实际产物，记录停点、未决问题和授权边界。只交付文档也可能需要恢复入口；结果报告不能替代 handoff。只读请求或用户限定仅输出指定文件时不额外写入，交付时说明尚无恢复入口。

## 提取当前 MVP

使用 [子设计模板](../assets/mvp-design.template.md)，顶部写清总目标关联、一个明确结果、最小验收链、必须保留的职责和本轮不做的事。技术试验可独立验收，但不能因此宣称用户已获得可用产品。

每次提取子设计、写计划、加入新工作、发现反例及复核时，判断：**省略这项会使当前验收失败，或违反已确认约束吗？**

判断依据是用户已确认的交付目标、验收和后续明确决定，不仅是最新 design／plan。保留这些决定的可定位依据，复用设计中的既有说明或来源引用即可。Agent 自行更新文档、审查者提出建议或用户授权“继续执行”，都不能单独证明新增范围已获批准；若文档已被自行扩大，指出差异并在维护授权内纠正受影响部分，不把新增内容当作既定要求，也不擅自删除已有成果。

- 会：纳入最小必要范围；实质改变目标、共享接口、验收或成本时说明取舍，由主会话／用户决定。
- 不会：延后或不记录；只有有价值的延后项才写重新考虑的触发条件。
- 不确定：做最小检查，不先搭建通用平台或完整治理系统。

减少范围不能删除核心职责、原失败样例或约定的正确性。缺口会使实际运行违反既定边界时，只暂停受影响运行。

同一子设计可以同时有已定部分、待验证候选和延后项。实现 plan 只承接当前已定且获授权部分；一份 plan 完成不能把整个设计／MVP 标为完成。

分别表达设计、实现、验收、交付状态。例如“方案已定、已整合、静态检查通过但真实入口未验证、本地未提交”。不强制状态机，不把 commit 当成验收。

共享规则由总设计或指定的唯一子设计承载，其余引用。总设计委派的细节以对应子设计为准；改变总设计不变条件须回主会话处理。文档与代码不符时指出差异，不能用文档覆盖事实。

## 重要未知：先验证，再定实现

先在子设计记录问题、为何阻碍当前 MVP、候选方案及代价、最小检查、成立／不成立／证据不足后的去向，再按需写验证 plan。已有资料足以回答时直接调查，不为模板新增研究任务。

验证可以包含获授权的可逆原型。结束于足够支持决策的证据或约定投入边界：

- 成立：回写适用版本、条件和选定契约。
- 不成立：保留反例，采用备选或调整设计。
- 不足：写清缺少什么、影响和下一项有价值的检查，不无限研究相邻问题。

原型不自动成为产品代码。选择性复用时核对当前设计与主区基线，并完成接入后的验收。验证 plan 可结束并删除，MVP 仍可能未完成；删除前按协作参考保存有用判据与结论。

## 写可交接的 plan

具体任务组织、接口自查和交接方法由 `fucxxx-codex-spec-plan` 维护，按主入口能力路由实际读取。使用本包 Plan 模板，计划只承接当前设计；作用点、范围依据、未知去向服从本文，执行和收口服从协作参考。不在此重复另一套任务步骤。

## 小改动与设计变化

文案、简单配置或既定行为修复：核对约束后直接修改和验证，有相关子设计时复用；没有时不为挂靠补造 MVP。不强制 plan、子会话或完整收口；只有设计决策、交接或恢复确有需要时增加相应内容。

只更新实际受影响的说明、验收结论或限制。一次完成且无待交接状态可直接报告；有在途工作、阻塞或待恢复下一步时由主会话更新 handoff。小改动若变成目标／契约变化，再按重要取舍处理；不能借“小修改”降低验收。
