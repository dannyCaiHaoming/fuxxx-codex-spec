# 计划能力

输入是当前目标、权威设计及基线、授权边界；输出是执行者无需重猜设计即可使用的 plan。计划组织执行，不取代设计。

## 读取与进入条件

实际读取主 Skill `fucxxx-codex-spec`、其 `references/design-and-plan.md` 及项目当前设计、已有活动 plan。优先读取宿主提供的入口；仓库并列布局可读 `../fucxxx-codex-spec/SKILL.md`，安装后不假定此布局。缺少主入口时报告缺口，继续可做的只读分析，不自动安装或虚构已加载。读取共同约束后直接执行本能力，不循环派回自身。

只读审阅不修改文件；小改动可直接走主入口轻量路径。实施 plan 只承接已定且获授权部分。发现关键契约缺口时指出证据与影响，回设计处理；重要未知可形成验证 plan，不能偷偷选择产品行为来把任务填满。已经明确的需求不重新 brainstorm。

## 组织可执行任务

使用主包 `assets/plan.template.md`，保存到既有项目资料位置，不创建自己的计划树。先核对真实代码结构、职责和现有测试入口，再安排任务；只列当前需要的修改位置，不因规划机会重构仓库。

每个任务以可观察产出为单位，准备、配置和文档归入服务的交付；只在能独立验证且接口清楚时拆开。任务间存在依赖就注明顺序，不把不同层的半成品当成独立 MVP。

让执行者明确以下内容：

- 输入来源、输出使用者，以及跨任务交接的接口名称、参数、返回值、错误语义；设计已固定的值准确传递，其余普通内部细节留给执行者。
- 涉及文件与直接依赖、为何服务当前目标、改动作用点；引用设计，不另定范围。
- 关键测试输入及断言、实际可运行命令和预期结果。必要时给简短测试示例；常规实现不预写完整函数体。尚无测试入口时明确需要建立什么，不把拟建命令说成已经验证可用。
- 新行为或修复如何用失败证据／必要测试确认，再验证实现和约定集成链路。文案等低风险变更不强制制造测试，不能用形式化步骤代替有价值的验证。

步骤应能落实为明确行动，避免“完善处理”“适当测试”之类没有判据的任务，也不要规定执行者每次只能写一种代码。计划长于设计不自动错误，但大量重复代码或决定不了任何事情的文字应删去。

## 自查与交接

完成后对照设计检查：每项当前验收是否有承担任务；上下游接口和值是否一致；原始失败与设计直接蕴含的关键反例是否覆盖；任务输出、验证与结果位置能否对应。只补实际缺口，不为了凑固定数量新增风险和任务。发现相邻优化按共同范围规则延后。

修正本 plan 内的普通错误；实质设计变化交主会话更新权威设计及受影响计划。用户已选定执行方式就保留；未指定时可在授权与工具允许范围内选合适方式，不强制因计划完成再问一轮。派单写入归属、未提交依赖及契约变更恢复按主包协作参考处理，不引入额外 ledger。

### 一个具体例子

总目标是团队任务管理；当前 MVP 是已登录成员创建任务、列表可见且刷新后保留。保留团队权限、持久化和失败反馈，通知与审批仍为后续候选。

假设设计已明确 `POST /api/teams/:teamId/tasks` 的契约，下面是示例而非实际测试记录：

| Plan 位置 | “创建任务 API”任务 |
| --- | --- |
| 工作安排 | 复用登录身份和团队成员校验，接收标题，有权限时保存任务并返回 `201` 和 `id`；结果供页面和列表使用。此任务不实现页面交互。 |
| 验证方式 | 用真实 API 创建，再从列表读回相同 `id`；跨团队请求返回约定 `403` 且不新增记录。使用测试账号与测试数据库，命令取自项目实际入口。 |
| 执行结果写法 | 若创建和读回通过，但跨团队请求仍新增记录：记录各自证据，该任务未通过，先修权限路径。页面提交与刷新未验证，不能标记整个 MVP 完成。 |

若执行者提出先做通知中心，按当前 MVP 目标延后。若权限契约未知，先定位或做有界验证，不让实施会话自行选择多租户规则。


## 返回与继续

返回 plan 链接、承接的设计范围、剩余关键问题及本次交付终点。只写计划或先审阅就在此交付并保存必要 handoff；已授权开发完成且条件具备时，回到主入口的执行与复核方法继续。执行结果按原模板保存，结束后回写设计与长期证据再移除 plan；不把临时计划当永久唯一依据，不逐任务自动 commit。
